# 友達追加・申請承認・複数インスタンス — 計画書

**ステータス:** 実装中  
**概要:** サンプルチャットアプリの「友達追加機能」（申請・承認フロー含む）と、PC 上で複数インスタンスを立ち上げて 2 者間通信を再現するための仕様・実装方針。

---

## 1. 友達追加と「つながり」のイメージ

- **つながり** = 相手の DID を連絡先に持ち、その相手とメッセージの送受信ができる状態。
- **DID は公開情報**。共有してよい。秘密にすべきは秘密鍵のみ。
- **申請・承認フロー**は、QR コード漏洩時を想定して採用する。相手が承認するまで連絡先にはならない。

---

## 2. フロー（申請・承認）

1. **A が自分の DID を共有** — QR コード表示、またはテキストでコピー。
2. **B が A の DID を取得** — QR スキャン、または手打ち・コピペ。
3. **B が友達申請を送る** — B のアプリから「友達申請を送る」を実行。A の DID 宛に「友達申請」メッセージを 1 回送信（P2P）。
4. **A が申請を受信** — アプリで「申請一覧」に表示。
5. **A が承認 or 拒否** — 承認時のみ A の連絡先に B を追加。任意で B に「承認した」通知を送り、B の連絡先に A を追加。
6. **拒否** — 連絡先に追加しない。QR 漏洩時は第三者からの申請を拒否できる。

技術的には「友達申請」= その DID 宛の特別なメッセージ種別、「承認」= その DID を連絡先に追加するユーザー操作。

---

## 3. DID 入力方法

| 方法 | 用途 |
|------|------|
| **QR コード** | 相手が共有した QR をスキャンして DID を取得。主に友達申請を送る側で使用。 |
| **手打ち・コピペ** | DID をテキストで受け取った場合。入力欄に貼り付けまたは手入力。申請送信・直接追加の両方に対応。 |

UI では「DID 入力」を 1 つにし、QR スキャン結果も手打ちも同じフィールドに反映する。

---

## 4. 機能要件（友達追加・申請承認）

| 項目 | 仕様 |
|------|------|
| **QR 共有** | 自分の DID を QR コードで表示。共有ボタンまたは設定から表示。 |
| **DID 入力** | QR スキャンまたは手打ち・コピペ。簡易検証（`did:key:` で始まる等）。自分の DID は申請・追加不可。 |
| **友達申請** | 入力した DID 宛に「友達申請」メッセージを 1 回送信。既に連絡先の場合は申請不要。 |
| **申請一覧** | 受信した友達申請を一覧表示。送信元 DID・受信日時。 |
| **承認・拒否** | 承認時のみ相手を連絡先に追加。任意で「承認した」通知を相手に送り、相手側で A を連絡先に追加。拒否時は追加しない。 |
| **永続化** | 連絡先・申請一覧（未承認分）はインスタンスごとの userData に保存（後述）。 |

---

## 5. 複数インスタンス（PC 上で 2 者間を再現）

- **1 インスタンス = 1 ノード = 1 DID**。2 者間なら 2 インスタンス = 2 DID で問題ない。
- **分離するもの**: (1) identity（DID の元になる秘密鍵・identity ファイル）、(2) アプリのユーザーデータ（連絡先・メッセージ・申請一覧）。

### 5.1 管理方法

- **Electron の user-data-dir をインスタンスごとに分ける。**
  - インスタンス A: `electron . --user-data-dir=./data/userA`
  - インスタンス B: `electron . --user-data-dir=./data/userB`
- 各 userData 配下に保存するもの:
  - identity（core の linkself-daemon に渡す identityPath）
  - contacts.json（連絡先）
  - 申請一覧・メッセージ等（仕様に応じてファイル分割）
- linkself-daemon（core/cmd/linkself-daemon）起動時に、そのインスタンスの userData に紐づく identity パスを渡す。daemon のソースは core 内にのみあり、chat-client 内に daemon ディレクトリはない。

### 5.2 開発・検証用（実装済み）

- **package.json**: `dev:userA`（Vite + Electron を `./data/userA` で起動）、`electron:userB`（Electron のみ `./data/userB` で起動）を追加済み。
- **2 インスタンスの起動手順**:
  1. ターミナル 1: `npm run dev:userA` — Vite と 1 つ目の Electron（userA の identity・連絡先）が起動する。
  2. ターミナル 2: `npm run electron:userB` — 2 つ目の Electron（userB の identity・連絡先）が起動する。Vite はターミナル 1 で動いているため、同じ React アプリを両方のウィンドウが読み込む。

---

## 6. 永続化の置き場所

- **Electron**: `app.getPath('userData')` 配下。user-data-dir を分ければインスタンスごとに分離される。
- **ファイル例**: `contacts.json`（連絡先）、`friend-requests.json`（未承認の申請一覧）。メッセージ履歴は別ファイルまたは同一ディレクトリ内に分割。
- **読み書き**: メインプロセスで行い、レンダラーとは IPC で「連絡先の取得・追加」「申請一覧の取得・承認・拒否」を提供する。

---

## 7. 実装タスク（粒度）

1. **永続化レイヤー** — userData 配下の contacts.json の読み書き。IPC ハンドラ（getContacts, addContact 等）。
2. **複数インスタンス対応** — 起動引数またはスクリプトで user-data-dir を切り替え。daemon に identityPath を userData 基準で渡す。
3. **友達追加 UI** — 「友達を追加」ボタン、DID 入力（テキスト＋QR スキャン）、バリデーション、申請送信。
4. **QR** — 自分の DID を QR 表示。相手の DID を QR スキャンして入力欄に反映。
5. **友達申請メッセージ** — 申請用メッセージ形式の定義。送信・受信時の「申請」判定と申請一覧への追加。
6. **申請一覧・承認・拒否 UI** — 申請一覧表示、承認・拒否ボタン、承認時に連絡先追加＋任意で「承認した」通知送信。
7. **起動時の読み込み** — 永続化した連絡先を起動時に読み込み、既存の onMessage で自動追加された分とマージして表示。
8. **送信前の connect** — 初回送信時または「接続」で daemon の `connect(peerDID)` を呼ぶ（任意だが推奨）。
9. **実運用を想定した検証** — LinkSelf 用 bootstrap ノードの運用（/linkself/did/ を扱う）。アプリのデフォルト bootstrap をそのノードのアドレスに設定し、BOOTSTRAP_PEER なしで 2 インスタンス同士が connect できることを確認する。詳細は [entry-point.md](entry-point.md#3-実運用を想定した検証)。
