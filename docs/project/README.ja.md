<a id="中央サーバーは便利ですでも"></a>
## 中央サーバーは便利です。でも…

中央サーバー（クラウド）があれば、いつでも、どこでも便利につながることができます。
ログインし、データを同期し、仲間とコミュニケーションできます。

- 中央サーバーはあなたの情報を覚えてくれているので、いつでもログインできます。
- 中央サーバーはあなたのデータを持っているのでどのデバイスからでも同期できます。
- 中央サーバーはあなたの（仲間との）つながりを覚えているのでいつでもつないでくれます。

「素晴らしい世界が来た」と感じたものでした。

しかしこういう言い方もできます。

- 中央サーバーはあなたの全てを知っている。
- 中央サーバーはあなたのデータを掴んでいる。
- 中央サーバーはあなたのつながりも抑えている。

<a id="サービス運営コスト"></a>
### サービス運営コスト

加えて、あなたがクラウド上で便利なサービスを提供したいと思うと、クラウドプラットフォーマーにたくさんのお金（サーバー費用）を払わなくてはなりません。

市場（いちば）の顔役にショバ代やみかじめ料を払うのと同じです。

<a id="自由と検閲"></a>
### 自由と検閲

現代ではほとんどの国や地域で「表現の自由」や「結社・集会の自由」が保証されています。しかし政府当局が「これは危険な人々の集会だ」と判断する場合においてはその限りではありません。なぜなら彼らには一般大多数の人々の日々の安全を守る責任があるからです。

そのような場合、政府はクラウドプラットフォーマーに情報開示を命令する権限があります。

- では誰が、どのように「これは危険な人々だ」と判断するのでしょうか？
- 彼らが判断を間違えることや、その判断が捻じ曲げられることは決してないと言い切れるでしょうか？

<a id="1-didの生成と共有ここが私ですと伝える"></a>
#### 1. **DIDの生成と共有：「ここが私です」と伝える**

田中さんがLinkSelfをインストールして起動します。

```
田中さんのスマホ (リンクセルフ起動)
  ↓
秘密鍵を生成（端末内でのみ）
  ↓
DID生成：did:key:z6Mkha...（この秘密鍵から自動生成）
  ↓
田中さんが友人にシェア：
  「ここが私のDIDです：did:key:z6Mkha...」
```

**技術的詳細：**
- 秘密鍵はあなたの端末から絶対に出ません
- DIDはこの秘密鍵から暗号学的に導出されるため、改ざんできません
- QRコード、テキスト、リンクでシェア可能

---

<a id="2-相手への登録お気に入りのような感じ"></a>
#### 2. **相手への登録：「お気に入り」のような感じ**

友人（ユキさん）がこのDIDをスキャンして、自分のLinkSelfに登録します。

```
ユキさんのPC (リンクセルフ)
  ↓
田中さんのDIDを読み込み
  ↓
「連絡先」に追加
  ↓
ローカルに保存（この時点ではまだ接続していない）
```

**技術的詳細：**
- この情報はユキさんの端末に保存されるだけです
- 中央サーバーには何も送られません
- ユキさんの「連絡先」は、ユキさんの端末内だけに存在します

---

<a id="3-起動と登録ネットワークに参加"></a>
#### 3. **起動と登録：ネットワークに参加**

二人が同時にLinkSelfを起動します。

```
田中さん：
  「私、起動しました！」
  ↓ libp2p DHTに登録
  「DID: did:key:z6Mkha...
    IP: 203.0.113.45
    ポート: 5001
    接続方法: インターネット経由」
  ↓
ネットワーク上の複数ノードが情報を受け取り、保管

ユキさん：
  「私、起動しました！」
  ↓ libp2p DHTに登録
  「DID: did:key:z6MkyB...
    IP: 198.51.100.78
    ポート: 5001
    接続方法: インターネット経由」
  ↓
ネットワーク上の複数ノードが情報を受け取り、保管
```

> **「ノード」とは何か？**
> 
> **ノード = 起動しているLinkSelfのインスタンス（デバイス）です。**
> 
> ```
> 例：
> - 田中さんのスマホ が起動 → 1つのノード
> - ユキさんのPC が起動 → 1つのノード
> - 太郎さんのタブレット が起動 → 1つのノード
> - あなたのノートパソコン が起動 → 1つのノード
> - 誰か他の国の人のデバイス が起動 → 1つのノード
> 
> → すべてがlibp2p ネットワークに参加
> → すべてが「電話帳」の一部を管理
> → 誰もが対等（中央のボス がない）
> ```
> 
> **重要：ノード = サーバーではない**
> 
> - サーバー：通常、24時間稼働している、巨大な企業が所有している、特別な機械
> - ノード：あなたのスマホ、PC、誰かのラップトップ。いつ起動してもいいし、いつ落としてもいい
> 
> **ノードの役割：**
> 
> 1. **自分の情報を登録する** → 「私はここにいます」と申告
> 2. **他人の情報を一部保管する** → libp2p DHTの一部を担当
> 3. **他人の検索に答える** → 「その人ならあっちにいますよ」と教える
> 4. **メッセージをリレーする** → 「この人へのメッセージ預けときますね」と受け取る
> 
> どのノードも同じ仕事をしています。だから、**特定のノードが壊れても、全体は動き続けます。**

**技術的詳細：**
- 「起動情報」の登録は、複数のlibp2pノードに自動的に分散保管されます
- TTL（Time To Live）付きで保管。一定時間たつと期限切れになります
- ノードが再起動すれば、自動的に新しい情報で上書きされます

<a id="4-発見と接続相手を探す"></a>
#### 4. **発見と接続：相手を探す**

ユキさんが、田中さんにメッセージを送ろうとします。

```
ユキさんのPC：
  「田中さんに連絡したい」
  ↓ libp2p DHTを検索
  「DID did:key:z6Mkha... の人、どこですか？」
  ↓
ネットワーク上のノードが答える
  「その人のIP: 203.0.113.45、ポート: 5001 です」
  ↓
ユキさんのPC
  「203.0.113.45:5001 に接続します」
  ↓
田中さんのスマホが接続を受け取る
  「ユキさんからの接続要求ですね。本人確認します」
  ↓
秘密鍵で署名検証（チャレンジ・レスポンス）
  ↓
接続確立！
```

**技術的詳細：**
- DID検索は、複数ノードに問い合わせされます。信頼性が上がります
- 接続確立時に、秘密鍵を使った相互認証が行われます
- 通信内容はエンドツーエンド暗号化されます（中間ノードは見えません）

<a id="5-メッセージ同期遅延送付の力"></a>
#### 5. **メッセージ同期：「遅延送付」の力**

田中さんがオフラインになった場合でも、リンクセルフは諦めません。

```
ユキさんが田中さんにメッセージ送信：
  「明日、コーヒー飲もう！」
  ↓
田中さんが現在オフライン
  ↓
ユキさんのPC：
  「送信失敗。でも保存しておこう」
  ↓ ローカルストレージに保管

30分後、田中さんがオンライン（WiFi接続）
  ↓
田中さんのスマホ：
  「起動したぞ。ネットワークに登録」
  ↓
ユキさんのPC：
  自動的に検知（またはDHT再検索）
  ↓
  「あ、田中さん起動した。待ってたメッセージを送ろう」
  ↓
メッセージ配信成功！
```

**技術的詳細：**
- 「Store-and-Forward」パターンの実装
- ユキさんの端末が、メッセージをローカルキャッシュ
- 相手が起動したら、自動的に同期開始
- DHT登録情報の有効期限が切れても、別のノードから相手を探す試みが続く

<a id="6-複数デバイス同期あなたのネットワーク"></a>
#### 6. **複数デバイス同期：「あなたのネットワーク」**

田中さんは、スマホ、PC、タブレットを持っています。

```
田中さんのスマホ：DID: did:key:z6Mkha...

  ↓ 起動時に自動同期設定
  
田中さんのPC：DID: did:key:z6Mkha... (同じDID)
  ↓
タブレット：DID: did:key:z6Mkha... (同じDID)

  ↓
ローカルネットワーク上で自動発見（mDNS）
  ↓
相互に同期開始
  ↓
すべてのデバイスのデータが一致
  ↓
ユキさんから見ると、「田中さん」は1つのアイデンティティ
```

**技術的詳細：**
- 同じ秘密鍵を持つ複数デバイス = 同じDID
- ローカルWi-Fi上では mDNS で自動発見
- インターネット経由でも、libp2p DHT で自動発見
- 各デバイスはピア・ツー・ピアで同期（中央サーバーなし）

<a id="7-グループ化と信頼ネットワーク私たちの繋がり"></a>
#### 7. **グループ化と信頼ネットワーク：「私たちの繋がり」**

田中さん、ユキさん、太郎さんで、「開発チーム」グループを作ります。

```
各自が「開発チーム」というグループの識別子を共有
  ↓
グループ内のメッセージは、メンバー間だけで同期
  ↓
グループ情報もlibp2p DHTで分散管理
  ↓
政府や企業がこのグループを「危険」と判断しても、
中央で一括削除する場所がない
  ↓
各個人のデバイスに情報が分散しているため、
つながりは永遠に残る
```

**技術的詳細：**
- グループのメタデータは、DHT上で管理
- メンバーの追加・削除も、メンバー間の投票で決定（民主的）
- グループのメッセージは、通常のメッセージとは別のマルチキャスト送信
- Merkle Tree で履歴検証（改ざん防止）

<a id="補足要点だけ"></a>
#### 補足：libp2p DHTに「自分とは関係のない」情報は保存されるか？

これは重要な質問です。答えは **「はい、保存されます。でも、心配することはありません」** です。

##### libp2pを使うと、LinkSelf以外の人々もネットワーク上にいることになるか？

**短く言うと：** インフラの「土台」は共有されることがあるが、**LinkSelfの「会員」になれるのはLinkSelfを動かしている人だけ**です。

- **土台の共有（オプション）**  
  libp2pはIPFSやFilecoinなど他のプロジェクトでも使われています。  
  - 同じ公的なDHT・ブートストラップを使う場合、**同じインターネット上で、LinkSelfノード以外のlibp2pノード（IPFSなど）も存在している**状態になります。  
  - それらは「経路」や「電話帳の問い合わせ先」として役に立つことがありますが、**LinkSelfのプロトコルは話さない**ので、アプリとしては「LinkSelfの人」にはなりません。

- **アプリの世界は分離している**  
  LinkSelfは独自のプロトコル名（例：`/linkself/...`）で通信します。  
  - 他のアプリ（IPFSなど）は別のプロトコル名を使うため、**同じノードがいても、LinkSelfのメッセージのやりとりに参加するのはLinkSelfを動かしているノードだけ**です。  
  - つまり「ネットワーク上にいる」のは、場合によっては「LinkSelf以外のlibp2pノードも含む」が、**「LinkSelfのネットワークの一員」になれるのはLinkSelfユーザーだけ**です。

- **完全に分離することも可能**  
  運用方針として、**LinkSelf専用のブートストラップやスウォーム鍵だけを使う**ようにすれば、LinkSelfノード同士だけでネットワークを構成できます。  
  - その場合は「ネットワーク上にいる」のは**LinkSelfを動かしている人だけ**になります。

##### libp2pでソケット通信を確立すると、ビデオ通話などもできるか？

**短く言うと：** **できます。** libp2pで張った「通信路」の上に、アプリ側でビデオ／音声を載せればビデオ通話も実現できます。

- **libp2pが用意するもの**  
  libp2pでピア間の接続ができると、**双方向・多重化・暗号化されたストリーム**が使えます。  
  - この上で送るデータの中身はアプリ任せなので、**テキスト・ファイル・音声・映像**など何でも流せます。  
  - つまり「ソケット通信を確立した」状態の延長で、**ビデオ通話用のストリームも同じ仕組みで扱える**ということです。

- **ビデオ通話に必要なこと（アプリ側）**  
  1. **デバイスからの取得** … カメラ・マイクの映像・音声を取得（各OS／ブラウザのAPI）。  
  2. **符号化** … 映像は VP8 / H.264 など、音声は Opus などでエンコード。  
  3. **libp2pストリームで送受信** … 上記データを libp2p のストリームで送り、相手側でデコードして再生。  
  4. **遅延・帯域の調整** … ビットレートや解像度を状況に合わせて変える（実装次第）。

- **WebRTC は理念上は非推奨**  
  WebRTC は STUN／TURN サーバーやシグナリング用サーバーに依存することが多く、**限られた情報とはいえサーバーを持つ／使う形になりがち**です。LinkSelf の「サーバーは不要」「主権ある個人」という理念からは、**WebRTC に頼る方式は非推奨**と考えます。  
  - ビデオ通話は **libp2p のストリームの上に、アプリ独自のメディアプロトコル（符号化・送受信・再生）を載せる**形で実現するのが筋が良いです。  
  - ピア発見・経路・データのやりとりまで libp2p に統一すれば、**サーバーなしでビデオ通話も可能**になります。

##### DHTの仕組み：「公衆電話帳」のようなもの

```
libp2p DHT全体：
  ┌─────────────────────────────────────┐
  │ DID: did:key:z6Mkha... (田中さん)    │
  │ IP: 203.0.113.45                    │ ← 保存されている
  │                                     │
  │ DID: did:key:z6MkyB... (ユキさん)   │
  │ IP: 198.51.100.78                   │ ← 保存されている
  │                                     │
  │ DID: did:key:z6Mkzc... (太郎さん)   │
  │ IP: 192.0.2.100                     │ ← 保存されている
  │                                     │
  │ DID: did:key:z6Mkxd... (知らない人) │
  │ IP: 203.0.113.200                   │ ← 保存されている
  │          ↑ 自分とは関係ない          │
  └─────────────────────────────────────┘
```

**重要な違い：**

| 中央サーバー | libp2p DHT |
|-----------|-----------|
| 全員のデータが1箇所に集中 | データが分散保管 |
| 企業が「全員」を監視できる | 各ノードが自分の担当分だけ持つ |
| 全員のプライバシーが一点集中 | 誰もが全体を把握できない |

##### あなたのデバイス（ノード）は何を保存するか？

あなたのデバイスが起動したとき、以下の情報が保存されます：

**1. 自分の情報（必ず保存）**
```
- 自分のDID
- 自分のIPアドレス
- 自分のポート番号
- 自分の秘密鍵（端末内のみ、ネットワークに送られない）
```

**2. 「関連ノード」の情報（自動保存）**
```
- 自分が接続したノードのDID
- 自分の連絡先に登録してある人のDID
- 自分が同期中のノードのDID

← これらは「あなたにとって関連のある」ノード
```

**3. 「DHTの一部」をリレー役として保管（ランダム）**
```
- あなたのDIDのハッシュ値の「近所」にある
  他の人のDID情報が、一時的に保管される

例えば：
  あなたのDID: did:key:z6Mkha...
  ↓ ハッシュ化
  ↓ Kademlia距離が近いDIDの情報が保管される
  → did:key:z6Mkha2...
  → did:key:z6Mkha3...
```

> **Kademliaとは何か？**
>
> Kademliaは、分散ネットワークで「データをどこに置くか」と「データをどこから探すか」を決めるアルゴリズムです。BitcoinやDHT全般で使われている重要な技術です。
>
> ##### 例え：「図書館の配置」
>
> 普通の図書館：
> ```
> 司書が全ての本の位置を管理
>  ↓
> 「天才数学者の伝記」を探す
>  ↓
> 司書に聞く：「数学のコーナーは3階です」
> ```
>
> Kademliaネットワーク（分散図書館）：
> ```
> 図書館スタッフが地方に分散している
> 各スタッフは「近い番号の本」を担当
>
> 例：
> - スタッフA：001〜100番の本を担当
> - スタッフB：101〜200番の本を担当
> - スタッフC：201〜300番の本を担当
>
> 「天才数学者の伝記（ID: 150）」を探す
>  ↓
> 「150番を担当しているのは誰？」と問い合わせ
>  ↓
> スタッフB が見つかる
>  ↓
> スタッフB「はい、この本持ってます」
> ```
>
> ##### libp2pでのKademliaの動き
>
> ```
> あなたのDID: did:key:z6Mkha...
>  ↓ SHA-256でハッシュ化
>  ↓ 256ビットの長い数字になる
>     例：0x1a2b3c4d5e6f7g8h9i0j1k2l3m4n5o6p...
>
> libp2p DHT全体を、このハッシュ値の「範囲」で分割
>  ↓
> 各ノードが、特定の「範囲」を担当
>  ↓
> あなたのハッシュ値0x1a2b3c...は
> ノード X が管理する範囲に入る
>  ↓
> あなたの登録情報は「ノード X」に保管される
>
> 後で、誰かが「did:key:z6Mkha...どこ？」と検索
>  ↓
> 「ハッシュ値 0x1a2b3c... を担当しているノードは？」
>  ↓
> DHT網を辿ってノード X に辿り着く
>  ↓
> ノード X「はい、ここです」と教える
> ```
>
> ##### なぜKademliaなのか？
>
> **効率的：** ハッシュ値を見るだけで、どのノードに問い合わせるか決まる。だから、検索が高速
>
> **分散的：** 特定のノードに集中しない。「距離が近い」複数のノードが同じ情報を持つから、冗長性がある
>
> **スケーラブル：** ノード数が増えても、検索時間は増えない（logN のオーダー）
>
> ```
> 10個のノード → 平均 3ホップで見つかる
> 100個のノード → 平均 7ホップで見つかる
> 1000個のノード → 平均 10ホップで見つかる
> 100万個のノード → 平均 20ホップで見つかる
>
> ← ホップ数が対数的に増えるだけ
> ```
>
> ##### プライバシーとの関係
>
> **「あなたのDIDがどのハッシュ値になるか」は予測不可能**
>
> ```
> did:key:z6Mkha... → SHA-256 → 0x1a2b3c...
>                                    ↑ ランダムに見える
>
> did:key:z6Mkha2...→ SHA-256 → 0xff00aa...
>                                    ↑ 全然違う場所
> ```
>
> だから、ハッシュ値から「オリジナルのDID」を逆算することはできません。
>
> **DHTに登録されているのは「ハッシュ値」と「ネットワークアドレス」だけ**
>
> ```
> DHTに見える情報：
>   0x1a2b3c... → IP: 203.0.113.45
>
> DHTに見えない情報：
>   - 0x1a2b3c... が「誰のDID」か
>   - その人が「何をしているか」
>   - その人の「本当の名前」は？
> ```
>
> だから、**DHTをスキャンしても、個人を特定できない**というわけです。

---

ここが重要です。

```
あなたのノード（ノード A）が保管している情報：

✅ 見える情報：
   - 自分の情報
   - 自分が知っている人の情報
   - DHT上で「近い」DIDの情報（でも、個人は特定できない）

❌ 見えない情報：
   - 他人同士の通信内容
   - 他人の詳細なプロフィール
   - 「全体」のユーザーリスト
   - 誰が誰とつながっているか（他人のコネクション）
```

##### 例：GoogleやFacebookとの違い

**Facebook（中央サーバー）：**
```
Facebook のサーバー：
  ↓ 全員のDIDを保管
  ↓ 全員のプロフィール写真を保管
  ↓ 全員の友人リストを保管
  ↓ 全員のメッセージを保管
  ↓ 全員の検索履歴を保管
  ↓ Facebookが「全員の情報」を持つ
  → 広告ターゲティング
  → 政府への情報提供
  → 個人的な判断で削除可能
```

**LinkSelf（分散型）：**
```
あなたのデバイス：
  ↓ 自分のDIDを保管
  ↓ 自分の連絡先のDIDを保管
  ↓ DHT上の「近所」のDIDを保管（でも内容は見えない）
  ↓ あなたはあなとつながっている人の情報しか見えない
  → 誰もが「全体」を把握できない
  → 個人の監視が不可能
  → 一括削除ができない
```

##### セキュリティ対策：「悪意のある参加者」への防衛

もし、あなたが「自分とは関係ない」ノードの情報をダンプしたら？

```
攻撃者のノード：
  「全員のDID集めてやろう」
  ↓ DHTを大量スキャン
  ↓ 100万個のDID情報を集める

しかし：
  ✅ DID だけでは、個人を特定できない
     （DIDは秘密鍵から生成される公開識別子）
  
  ✅ DIDだけでは、何をしているか分からない
     （通信は暗号化されている）
  
  ✅ IPアドレスも集められるが
     （VPN、プロキシで隠せる）
  
  ✅ そもそも、ノードは嘘をつける
     （偽の情報を登録することもできる）
```

##### 実装予定：信頼とレピュテーション

LinkSelfでは、以下のメカニズムを検討しています：

1. **レピュテーションスコア**
   - 誠実に情報を提供するノードを優遇
   - 嘘をつくノードを減点

2. **アクセス制御**
   - 大量のDHT問い合わせを制限
   - 短時間に全員のノードスキャンを防止

3. **情報の有効期限**
   - TTL（Time To Live）で期限切れにする
   - 古い情報は自動削除

4. **ノードの検証**
   - たまに「本当にここにいるの？」と確認
   - 応答しないノードを削除

##### 深堀り：悪意のあるアプローチと防御メカニズム

あなたの質問は重要です。**「もし攻撃者が、自分のデバイスに保存されている他人のハッシュを使ってアプローチできたら？」** という心配ですね。

**攻撃シナリオ：Sybil Attack（シビル攻撃）**

```
攻撃者が考えること：
  「じゃあ、オレのノードに大量の偽のハッシュ値を登録しよう」
  ↓
  0x1a2b3c... → 攻撃者のIP
  0x1a2b3d... → 攻撃者のIP
  0x1a2b3e... → 攻撃者のIP
  0x1a2b3f... → 攻撃者のIP
  （何百万個も）
  ↓
  誰かが「0x1a2b3d... どこ？」と検索
  ↓
  攻撃者のノードが「オレだ」と答える
  ↓
  検索者が、攻撃者のノードに接続してしまう
```

**これは本当に危険です。** しかし、LinkSelfに対する攻撃ではありません。むしろ、libp2p DHT全般への古典的な攻撃です。

**防御メカニズム1：「秘密鍵によるカバー」**

重要なのは、**検索者がDIDに接続しようとするとき、秘密鍵による認証が必須**ということです。

```
検索者が攻撃者のノードに接続

検索者：
  「did:key:z6Mkha... に接続したいです」
  ↓
攻撃者のノード：
  「はい、それは私です」
  ↓
検索者：
  「では、秘密鍵で証明してください。
   このランダムな値に署名してください」
  ↓
攻撃者のノード：
  「... 秘密鍵を持ってない 😭」
  ↓
接続失敗・拒絶
```

**つまり、たとえハッシュが正しくても、秘密鍵がなければ本人になりすましはできません。**

**防御メカニズム2：レピュテーション・スコア（信頼スコア）**

各ノードが「信頼度」を持つようにします。

```
新しく接続したノード：
  レピュテーションスコア = 0（未知数）
  ↓
正しい情報を提供した
  ↓
レピュテーションスコア = +1
  ↓
信頼度が上がると：
  - DHTへのクエリ回答の優先度が上がる
  - 保管する情報量が増える

逆に、嘘をついたノード：
  ↓
レピュテーションスコア = -1
  ↓
信頼度が下がると：
  - DHTから削除される
  - ブラックリストに入る
```

**防御メカニズム3：ビザンチン障害耐性（Byzantine Fault Tolerance）**

複数のノードに同時に問い合わせて、答えを検証します。

```
検索者が「did:key:z6Mkha... どこ？」と問い合わせ
  ↓
複数のノード（K個）に同時に問い合わせ

ノード A：「IP: 203.0.113.45」
ノード B：「IP: 203.0.113.45」
ノード C：「IP: 攻撃者.com」（嘘）
ノード D：「IP: 203.0.113.45」
ノード E：「IP: 203.0.113.45」
  ↓
多数決：203.0.113.45 が勝つ
  ↓
検索者は正しいIPに接続
```

**防御メカニズム4：「プルーフ・オブ・ワーク」的制限**

ノードが大量の登録をしようとすると、計算量的なコストを要求します。

```
攻撃者が100万個のDIDを登録しようとする
  ↓
各登録に対して「このハッシュを見つけてください」
という計算問題を出す
  ↓
SHA-256で検索して、特定の条件を満たすハッシュを見つける
  ↓
これには時間がかかる（Bitcoinのマイニングと同じ原理）
  ↓
攻撃者も時間とCPUコストを払わないといけなくなる
  ↓
収益性がなくなる → 攻撃が減少
```

**防御メカニズム5：タイムスタンプと有効期限**

登録情報に「いつ登録されたか」を記録し、古い情報は削除します。

```
攻撃者が登録：
  0x1a2b3c... → 攻撃者のIP（タイムスタンプ：2026年2月8日）
  ↓
1時間後、TTL期限切れ
  ↓
自動削除
  ↓
攻撃者は何度も何度も再登録する必要がある
  ↓
再登録には「プルーフ・オブ・ワーク」が必要
  ↓
資源浪費が増加 → 攻撃が採算に合わない
```

**防御メカニズム6：自動的な拒絶：署名検証**

これが最も重要です。**すべての接続時に秘密鍵による署名検証が自動的に行われます。**

```
ユーザーが何もしなくても、以下が自動実行される：

1. DHTからIPアドレスを取得
2. そのIPアドレスに接続試行
3. 相手に「チャレンジ」を送信（ランダムな値）
4. 相手が秘密鍵で署名した「レスポンス」を待つ
5. 署名を検証
   - OK  → 本人確定、接続成功
   - NG  → 本人ではない、自動拒絶
```

ユーザーは、この認証を意識する必要はありません。すべて自動です。

**実例：Bitcoinのマイニング難易度調整**

Bitcoinも同じ問題に直面していました。

```
Bitcoinの場合：
  - 新規ノードが大量に偽のトランザクションを送信
  - マイニング難易度を上げることで対抗
  - 攻撃者も莫大なコンピュータ資源が必要に
  - 結果：採算に合わない → 攻撃が減少
```

LinkSelfでも、これと同様の方法を取ります。

---

**まとめ：悪意のあるアプローチは可能か？**

| 攻撃方法 | 可能性 | 防御方法 |
|---------|--------|---------|
| **偽のハッシュ登録** | ❌ 止められない（そもそも分散なので） | ✅ 署名検証で自動拒絶 |
| **本人になりすまし** | ❌ 秘密鍵がないので無理 | ✅ 秘密鍵による認証が必須 |
| **大量登録** | ❌ プルーフ・オブ・ワークで制限 | ✅ 自動的に計算コスト増加 |
| **古い情報を保持** | ❌ TTLで自動削除 | ✅ 有効期限で対応 |
| **複数ノードからの嘘** | ❌ 多数決で検証 | ✅ ビザンチン障害耐性 |

**結論：**
- 攻撃者が「偽の情報を登録する」ことは止められません（分散システムだから）
- しかし、**その偽の情報を「使う」ことは自動的に拒絶されます**
- なぜなら、秘密鍵による署名検証が自動的に行われるから
- つまり、攻撃は「可能だが無意味」になります

<a id="まとめ何がすごいのか"></a>
### まとめ：何がすごいのか

この一連のやり取りで、**一度も中央サーバーが出てきていません。** 

- ✅ DIDはあなたのデバイスで生成
- ✅ 相手との繋がりはあなたのデバイスで管理
- ✅ ネットワーク情報はlibp2p DHTで分散管理
- ✅ メッセージはエンドツーエンド暗号化
- ✅ グループもあなたのデバイスで管理

**つまり、あなたのデータ、あなたの繋がり、あなたのコミュニティは、完全にあなたのもの。誰にも支配されません。**


<a id="technical-approach"></a>
## 🛠 Technical Approach（技術の要点）

ピアの見つけ方・接続・同期の流れは、上記の「シナリオ：田中さんとトモダチ」でストーリーとして書いています。

技術スタックの要点だけ：

- **DID（did:key）** … オフラインでも作れる自己証明のID。秘密鍵から導出、改ざん不可。
- **libp2p DHT** … DIDと「今どこにいるか」を分散の電話帳で管理。中央サーバーなし。Bitcoinと同じ考え方。
- **経路** … DHT検索のほか、mDNS（同一Wi-Fi）、Bluetooth、リレー、手動共有（QRなど）。
- **本人確認** … 接続時に秘密鍵でチャレンジ・レスポンス。なりすましは自動拒絶。
- **Cross-Platform** … Goコアを各プラットフォームでライブラリとして利用可能。UI はプラットフォームに合わせて選択（例: Electron, Flutter, ネイティブ）。
- **Local-first Sync** … Store-and-Forward。相手がオンラインになったら同期。
