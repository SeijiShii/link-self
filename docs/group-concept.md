# グループの概念

**参照:** [Phase 1 設計](phase1-design.md)、[分散ネットワーク DB 化計画](sync-db-plan.md)

---

## 1. 概要

- **グループ** = メンバー（DID）の集合。**最低 2 人**。
- **1 対 1** は「2 人グループ」のケースとして扱う。1 対 1 専用の概念は持たない。
- グループのメンバーリスト・オーナー情報は各ノードがローカルに保持する（DHT 上にグループ実体は持たない）。
- **編集・閲覧権限**などの切り分けは、ネットワークのグループ概念ではなく**アプリ側のレイヤー**で行う。コアのグループは「誰がメンバーか」「誰がオーナーか」までを扱い、権限の詳細はアプリが定義する。

---

## 2. 自分が所属するグループの情報はどこに保持するか

- **インフラとして提供**する。グループ情報（自分が所属するグループ一覧・各グループのメンバー DID・オーナー情報）の保存は、**インターフェース化**し、実装はインフラに含める。**最終的には SQLite3 等で実装するが、呼び出し側はインターフェースに依存する**形にする。
- **インターフェース**: グループ一覧の取得・追加・更新・削除、および「groupId → メンバー DID リスト・オーナー情報」の取得・保存に必要な操作をインターフェースで定義する。コア・同期レイヤ・アプリはこのインターフェース経由でのみグループ情報にアクセスする。
- **実装**: デフォルトとして **SQLite3 を用いた実装**をインフラに含める。スキーマ（グループテーブル、メンバー・オーナー情報）はインフラ側で定義するか、またはドキュメントで規約として示す。アプリはこの実装をそのまま使うか、インターフェースを満たす自前実装（テスト用インメモリ、別 DB など）を注入できる。
- **保持場所**: 各デバイス（ノード）のローカル。中央サーバーや DHT にはグループ実体を置かない（Phase 1 の前提）。SQLite3 実装の場合は、アプリが指定した DB パス（またはデフォルトパス）に保存する。
- **メリット**: (1) インターフェース化によりテスト時はモック・インメモリ実装に差し替え可能。(2) 将来の永続化先の変更（別 DB・暗号化レイヤーなど）がインターフェースの実装差し替えで済む。(3) コア・同期レイヤは「グループ情報の永続化」の詳細に依存しない。

---

## 3. メンバーと脱退

| 項目 | 内容 |
|------|------|
| **メンバー** | グループに属する DID のリスト。2 人以上。 |
| **脱退** | メンバーは**いつでも**グループを脱退できる。 |
| **2 人グループ** | メンバーが 2 人のとき、片方が脱退するとそのグループは**解体**される。 |

---

## 4. オーナー（管理者）

| 項目 | 内容 |
|------|------|
| **オーナー** | グループには**オーナー**（管理者）の概念がある。 |
| **2 人のとき** | メンバーが 2 人の場合はオーナー概念を**隠匿してよい**（片方が抜ければグループ解体のため、運用上区別しない）。 |
| **3 人目招待時** | 3 人目のメンバーを招待するとき、最初の 2 人のうち**どちらか、あるいは両方**をオーナーにするかを決定する。 |

### オーナーの権限

| 権限 | 内容 |
|------|------|
| **メンバー削除** | オーナーはメンバーを削除できる（キック）。 |
| **オーナー任命** | オーナーは他のメンバーをオーナーに任命できる。 |
| **自己降格** | オーナーは自身をオーナーやめてメンバーに降格できる。 |
| **他オーナー降格** | オーナーは**他のオーナーを降格できない**。 |

---

## 5. 最後の 1 人のオーナーが降格・脱退したとき

- 最後の 1 人のオーナーが**自己降格**または**脱退**すると、オーナーが 0 人になる。
- このとき**残りメンバーの誰か 1 人（以上）を自動でオーナーに昇格**させる（オーナー 0 人の状態は作らない）。

### 新オーナーの決め方

| 方式 | 内容 |
|------|------|
| **任意で決定** | 残りメンバーの中から、任意のルール（指名・参加順など）で誰をオーナーにするか決める。この場合「最後の 1 人」にしないようにする（例: 残りが 2 人以上いるときはオーナーを 2 人昇格させる）。 |
| **ランダムで決定** | 残りメンバーの中からランダムに 1 人を選んでオーナーにする。 |

---

## 6. 権限はアプリ層で扱う

- **ドキュメントの編集権・閲覧権**の切り分けや、リソース単位のアクセス制御は、**ネットワークのグループ概念ではなくアプリ側のレイヤー**で行う。
- コアのグループは「メンバー」「オーナー」「脱退・解体・招待・キック」といった**グループのライフサイクル**のみを扱う。
- アプリは、グループ（メンバー・オーナー）の上に、独自の権限モデル（編集可／閲覧のみ、ドキュメント別など）を載せる。
